The fork's `Agent` / `agent_team` tools and `--agent-team-subagent-skills` flag collide with the
installed packages it replaces: `@tintinweb/pi-subagents` (provides `Agent`) and `npm:pi-multiagent`
(provides `agent_team`). Loading the fork on a full `pi` throws `Tool "Agent" conflicts...` /
`Tool "agent_team" conflicts...` and the npm packages fail to load. So there are two launch options:

### Option C (RECOMMENDED for the interactive operator smoke; previews 7.8)
Temporarily disable only the two conflicting packages, then run pi NORMALLY (full auth/model, no
`--no-extensions`, no startup 400). Verified headless: no conflicts, `Agent`+`run_status` work.

### Option A (isolated, headless-only-friendly)
```bash
cd /mnt/DEV/stellar
pi --no-extensions \
   -e /tmp/pi-multiagent-upstream/extensions/multiagent/index.ts \
   -e /tmp/pi-multiagent-upstream/extensions/orchestra/index.ts \
   --model openai/gpt-4o      # REQUIRED under --no-extensions (see note)
```
WARNING: Option A breaks the INTERACTIVE startup. `--no-extensions` disables the Anthropic OAuth
adapter + the provider that registers the default model, and Pi fires an empty request at interactive
startup -> `400 ... messages: at least one message is required`. `--model` does NOT prevent it
interactively. Option A only works headless (`-p`). Use Option C for the interactive operator smoke.

Notes:
- `--no-extensions` (Option A) avoids the conflict but breaks interactive auth/model startup.
- **`--model <built-in>` is REQUIRED with `--no-extensions`.** The settings default `anthropic/claude-opus-4-8` is registered by an extension (it appears only in `pi --list-models` *with* extensions; built-ins stop at `claude-opus-4-5`). Under `--no-extensions` that model is unresolvable, so Pi fires an empty request at startup and the REPL dies with `400 ... messages: at least one message is required`. Pin a built-in to avoid it: `--model openai/gpt-4o` (or `anthropic/claude-opus-4-5`, `openai/gpt-4o-mini`). Built-in anthropic models bill the raw `ANTHROPIC_API_KEY` (pay-as-you-go), not the exhausted OAuth "extra usage" subscription.
- Child personas use their own frontmatter models (e.g. `coding_reviewer` -> `anthropic/claude-sonnet-4-5`, a built-in).
- The interactive `/agent <persona> "<task>"` slash command does NOT need a parent model call; the headless `Agent` tool path does.

## Findings

### FIX-1 (applied) — fork did not load at all
`extensions/multiagent/index.ts:14` imports `prepareLibraryOptions` from `./src/library-policy.ts`, but that file was **dropped during the fork trim** (added upstream in `8c4f2da` 0.6.1, deleted in `80bc8a8` 0.9.3). Working tree was clean, so it was never recorded as a deletion — the module just goes missing → `Cannot find module './src/library-policy.ts'` → extension load fails.
- Fix: restored the last good version from history: `git checkout 80bc8a8^ -- extensions/multiagent/src/library-policy.ts`.
- Its imports (`agents.ts`, `schemas.ts`, `types.ts`) all resolve in the current tree; signature matches the `index.ts:293` call site.
- bun tests stayed green; they import source modules directly and never exercise `index.ts`, which is why this never surfaced before a real-Pi load.

### FIX-2 (applied) — `/agent` always fails in a normal skill-rich session
`MAX_CALLER_SKILLS = 128`. orchestra's `buildRuntimeOptions` passed `parentSkills: getParentSkillInventory(pi)` with **no** `subagentSkills` config. `readSubagentSkillConfig(undefined)` defaults to mode `"enabled"` → propagate all ~120+ skills → `subagent-skills-too-many` error → child never starts. The operator flag `--agent-team-subagent-skills disabled` does NOT help because the flag is registered by the *multiagent* extension and orchestra's separate `ExtensionAPI` returns `undefined` from `getFlag`.
- Fix: `extensions/orchestra/index.ts` now sets `subagentSkills`/`materializationDiagnostics` from `readSubagentSkillConfig(pi.getFlag(SUBAGENT_SKILLS_FLAG) ?? "disabled")` — safe default (pi-subagents semantics: children don't inherit caller skills), still honors the flag if readable.
- Verified: with skills loaded (no `--no-skills`), the `subagent-skills-too-many` error is gone and the `Agent` tool starts the run.

### PROVEN GREEN (core L6-minimal)
- `Agent` tool resolves the package persona `reviewer`, maps to a single-step detached graph, starts via `agent_team` substrate, returns `runId` (e.g. `r1`, status `running`).
- Child run reaches terminal **`succeeded`** (observed via `agent_team action="list"` → `detachedRuns[].status="succeeded"`).

### OPEN-1 (real, deeper) — `agent_team run_status <runId>` cannot find orchestra-started runs
`detached-registry.ts` is a module-singleton `Map`. `run_status` reads ONLY that in-memory map (no disk fallback; only `reattach` reads persistent state). orchestra (loaded as a separate `-e` extension) and the `agent_team` tool appear to get **separate module instances** of `detached-registry.ts`, so:
- orchestra registers the run in registry-instance-A (+ persists to disk),
- `agent_team run_status` reads registry-instance-B → `run-not-found`,
- `agent_team list` reads B **plus disk** → shows the run. (This reconciles "list sees it" vs "run_status doesn't.")
Candidate fixes (operator decision): (a) give `run_status`/`step_result` a persistent-disk fallback like `reattach`; or (b) load orchestra+multiagent in one shared module graph (single package manifest load) so the registry is a true singleton.

### OPEN-2 (latent) — per-process runId namespace collisions
runIds are per-process `r1,r2,...` and reset each launch. Persistent state from prior processes (`owner: orphan`) collides with new `r1` and produced `status=error` runs until the state dir was cleared. Matches the audit's deferred "full run-id namespace fix."
- Housekeeping: cleared `~/.local/state/pi-multiagent/runs/*` (22 orphan test runs created by these probes).

## OPEN-3 (expected substrate guard, not a fork bug) — bash personas + project-settings cwd

Interactive Option C reached graph planning and then failed with:
`start-planning-failed -> bash-project-settings-denied: Step coding-reviewer requests bash inside
project Pi settings at /mnt/DEV/stellar/.pi/settings.json`.

Cause: the `coding_reviewer` project persona declares `tools: read, bash, grep, find`. The inherited
substrate fail-closes a bash-capable child whose cwd contains a project-controlled `.pi/settings.json`
(project settings + shell = privilege-escalation risk). This is correct authority behavior, not a fork
regression. bash-free personas (e.g. package `reviewer`: read/grep/find/ls) plan and run fine.

Workarounds for the smoke:
- Slash path with a bash-free persona: `/agent reviewer "review <file>"`.
- coding_reviewer specifically: use the `Agent` tool with a tools override dropping bash, e.g.
  `Agent({ subagent_type: "coding_reviewer", tools: ["read","grep","find","ls"], prompt: "review <file>" })`.
  (`/agent <persona> <task>` cannot pass a tools override; the Agent tool can.)
- Or run from a cwd without project `.pi/settings.json` (not practical here — the persona lives in the
  workspace `.pi/agents/`).

Implication for the formal 7.7 cross-persona run: any persona that declares `bash` will hit this guard
from the workspace root; test those via the Agent tool tools-override, and test bash-free personas via
`/agent` directly.
